# 質問票の回答（2026-11-05）

## Q1. p.141 「オブジェクトは順序付けされていないプロパティ」という記述が有りましたが、試しに point1 = {x:1, y:2} と point2 = {y:2, x:1} を console.log したところ書いた順に表示されたので、追加された順序は保持されており、順序付けされていると言えるのでは無いかと思いました。ここでの「順序付けされていない」とは何をもって、そう言っているのでしょうか？

**質問の要約**: 実際には書いた順にプロパティが表示されるのに、なぜ本では「順序がない」と言っているのかを聞いている

**回答**: プロパティには配列のような位置がなく、名前で値を取り出すという意味です。列挙の順番は仕様で決まっていますが、単純な追加順ではありません。整数のキーが先に昇順で並び、そのあとに文字列のキーが追加順で並びます。

**出典**:

- [MDN: for...in（走査順序）](https://developer.mozilla.org/ja/docs/Web/JavaScript/Reference/Statements/for...in)
- [ECMA-262: OrdinaryOwnPropertyKeys](https://tc39.es/ecma262/#sec-ordinaryownpropertykeys)

## Q2. p.142 オブジェクトはオブジェクトリテラル、new キーワード、Object.create() 関数を使って生成することもできますとありますが、Object.create() 関数を使用して生成する場面はあるのでしょうか？Object.create() 関数を使用して生成するコードを見た記憶があまりなかったので質問させていただきました

**質問の要約**: Object.create() でオブジェクトを作るのはどんなときか、実際に使う場面があるかを聞いている

**回答**: 今の実務ではあまり使いません。主な用途は Object.create(null) で、プロトタイプを持たない空のオブジェクトを作り、キーと値を入れるだけの辞書として使う場面です。継承のための用途は、今は class 構文で書くのが普通です。

**補足（書き換えを防ぐ使い方）**: 本の p.145 にあるように、渡したオブジェクトを書き換えられたくないときに Object.create(o) を渡す使い方もあります。Object.create(o) は、o を継承した新しいオブジェクトを作ります。読み出しはプロトタイプチェーンをたどって o の値が返りますが、代入すると新しいオブジェクト自身にプロパティが作られて o の値を隠すだけなので、o は変わりません。ただし守れるのは 1 段目のプロパティだけで、`o.nested.y` のような入れ子のオブジェクトは書き換えられてしまいます。また、Object.keys や JSON.stringify は継承したプロパティを見ないので、受け取った側では「空のオブジェクト」に見える点にも注意が必要です。

**補足（辞書として使う方法）**: 辞書とは、キーを渡すと値が返ってくる表として使うオブジェクトのことです。`{}` は Object.prototype を継承しているので、入れていない `constructor` や `toString` などのキーが最初からあるように見えてしまいます（`{}["constructor"]` は undefined ではなく Object 関数を返します）。そのため、単語の出現回数を数えるときに "constructor" という単語が来ると、0 から数えられません。Object.create(null) は何も継承しないので、自分で入れたキーしかありません。ただ、今は同じ目的で Map を使うことも多いです。

**出典**:

- [MDN: Object.create()](https://developer.mozilla.org/ja/docs/Web/JavaScript/Reference/Global_Objects/Object/create)
- [MDN: 継承とプロトタイプチェーン](https://developer.mozilla.org/ja/docs/Web/JavaScript/Inheritance_and_the_prototype_chain)

## Q3. p.144 オブジェクトを生成する際、オブジェクトリテラル（let o = {}）を使うのと、コンストラクタ（let o = new Object()）を使うのとで違いはないのか？

**質問の要約**: `{}` と `new Object()` で、できあがるオブジェクトに違いがあるかを聞いている

**回答**: 引数なしなら同じ空のオブジェクトになります。違いが出るのは引数を渡したときで、new Object(1) のようにプリミティブを渡すと、ラッパーオブジェクトになります。

**補足**: プリミティブはオブジェクトではないのに `"abc".length` や `(1.5).toFixed()` が動くのは、プロパティにアクセスした瞬間に JavaScript がプリミティブを一時的にラッパーオブジェクト（文字列なら String、数値なら Number）で包み、使い終わったら捨てているからです（自動ボックス化）。`new Object(1)` は、この包みを捨てずに手元に残す書き方です。

`new Object(1)` で作られるのは Number オブジェクトそのもので、`new Number(1)` と同じものです（`Object()` は値の型に合ったラッパーを選んで作ります）。一方、`new` を付けない `Number(1)` はオブジェクトを作らず、プリミティブの `1` を返します。

**出典**:

- [MDN: Object() コンストラクター](https://developer.mozilla.org/ja/docs/Web/JavaScript/Reference/Global_Objects/Object/Object)
- [MDN: プリミティブ（ラッパーオブジェクト）](https://developer.mozilla.org/ja/docs/Glossary/Primitive)
- [ECMA-262: ToObject](https://tc39.es/ecma262/#sec-toobject)
- [ECMA-262: Object Initializer（Runtime Semantics: Evaluation）](https://tc39.es/ecma262/#sec-object-initializer-runtime-semantics-evaluation)

## Q4. p.153 課題で obj.hasOwnProperty() や obj.propertyIsEnumerable() などを使用すると、eslint でエラーになった。直接の呼び出しは危険なのでしょうか

## Q5. p.156 「Object.assign()メソッドには、引数として2つ以上のオブジェクトを渡します」とありますが、課題6.7のテストでは、コピー元に数値・真偽値・文字列・null・undefinedを渡すケースがありました。実際に本物のObject.assignに渡すと、nullとundefinedは無視され、文字列"abc"は {0:"a",1:"b",2:"c"} のようにコピーされ、数値と真偽値は何もコピーされませんでした。オブジェクト以外を渡したときの扱いはどういうルールで決まっているのでしょうか。また、コピー先（第1引数）に数値や文字列を渡すとオブジェクトに変換されて返ってくるようですが、こういう使い方をする場面はあるのでしょうか

**質問の要約**: Object.assign にオブジェクト以外を渡したときの挙動のルールと、コピー先にプリミティブを渡す使い道があるかを聞いている

**回答**: コピー元のプリミティブはラッパーオブジェクトに変換され、その列挙可能な独自プロパティがコピーされます。String のラッパーだけが添字のプロパティを持つので、文字列だけが 1 文字ずつコピーされます。null と undefined は変換できないので無視されます。コピー先にプリミティブを渡す使い方は、実務ではまずありません。

**補足**: 実際の動きは次のとおりです。

```js
Object.assign({}, "abc"); // { 0: "a", 1: "b", 2: "c" }（1 文字ずつコピーされる）
Object.assign({}, 1, true); // {}（何もコピーされない）
Object.assign({}, null); // {}（無視される）
```

String のラッパーオブジェクトは、1 文字ごとに `"0"`, `"1"`, `"2"` という列挙可能な独自プロパティと、列挙不可の `length` を持っています。一方、Number や Boolean のラッパーオブジェクトは独自プロパティを 1 つも持たず、中の値は内部スロット（プログラムから直接見えない場所）にしまわれています。Object.assign は列挙可能な独自プロパティだけをコピーするので、文字列の添字だけがコピーされます。

```js
const s = new String("abc");
Object.getOwnPropertyNames(s); // ['0', '1', '2', 'length']（独自プロパティすべて）
Object.keys(s); // ['0', '1', '2']（列挙可能なものだけ。length は列挙されない）

const n = new Number(1);
Object.getOwnPropertyNames(n); // []（独自プロパティは 1 つもない）
n.valueOf(); // 1（値は内部スロットにあり、メソッドを通して取り出す）
```

コピー先も同じくラッパーオブジェクトに変換されて返ります。

```js
const r = Object.assign(3, { a: 1 });
r; // [Number: 3] { a: 1 }（Node.js の表示。ブラウザでは Number {3, a: 1}）
typeof r; // "object"
r.a; // 1
r + 1; // 4
```

`[Number: 3] { a: 1 }` は、「中身の値が 3 の Number オブジェクトで、`a: 1` というプロパティを持っている」という意味です。3 は内部スロットの値でプロパティではなく、`r + 1` のように計算するときに取り出されます。`a: 1` はコピー元から書き込まれた普通のプロパティです。ただしコピー先が null や undefined だと変換できないので TypeError になります。Q3 の new Object(1) と同じ「ラッパーオブジェクト」の仕組みです。

**出典**:

- [MDN: Object.assign()](https://developer.mozilla.org/ja/docs/Web/JavaScript/Reference/Global_Objects/Object/assign)
- [ECMA-262: Object.assign](https://tc39.es/ecma262/#sec-object.assign)
- [ECMA-262: String Exotic Objects](https://tc39.es/ecma262/#sec-string-exotic-objects)

## Q6. p.170 JavaScriptの配列は特殊なオブジェクトで、整数添え字も単なるプロパティとしてふるまいます。配列というとメモリ上で隣り合っているから効率的に順番にアクセスできるといった、ただのオブジェクトとは違った特性を期待しますが、JavaScriptでもそのような特性を期待してもいいものでしょうか

**質問の要約**: JavaScript の配列も、C などの配列のように要素がメモリ上に連続して並び、高速にアクセスできると考えてよいかを聞いている

**回答**: 言語仕様としては保証されていません。ただ、実際のエンジンは配列の形を見て保存の仕方を変えていて、穴がなく型のそろった配列なら、C の配列のように速く扱えます。連続したメモリを確実に使いたいときは、型付き配列を使います。

**補足**: V8 は配列の中身の状態を「elements kind」として追跡しています。穴のない配列は PACKED、穴を作ると HOLEY に格下げされ、一度格下げされると元には戻りません。そのため、`a[100] = 1` のように飛ばして代入したり、整数の配列に文字列を混ぜたりすると、最適化が効きにくくなります。

**出典**:

- [MDN: Array](https://developer.mozilla.org/ja/docs/Web/JavaScript/Reference/Global_Objects/Array)
- [MDN: JavaScript の型付き配列](https://developer.mozilla.org/ja/docs/Web/JavaScript/Guide/Typed_arrays)
- [V8 公式ブログ: Elements kinds in V8](https://v8.dev/blog/elements-kinds)

## Q7. p.173 Array.fromは既に同じ動きをする記法があるのになぜES6で専用のメソッドが追加されたのでしょうか。他の言語と同じような使用感を提供するためでしょうか

**質問の要約**: スプレッド構文 [...x] で同じことができるのに、なぜ Array.from が別に用意されているのかを聞いている

**回答**: スプレッド構文ではできないことがあるからです。代表的なのが、1 から n までのような連番の配列を作る場面で、Array.from({ length: n }, (\_, i) => i + 1) と 1 行で書けます。length だけを持つオブジェクトは反復可能でないのでスプレッド構文には渡せませんが、Array.from なら配列にでき、第 2 引数の関数で各要素を作れます。

**補足**: 動きは次のとおりです。

```js
Array.from({ length: 3 }, (_, i) => i + 1); // [1, 2, 3]
[...{ length: 3 }]; // TypeError（反復可能でない）
new Array(3).map((_, i) => i + 1); // [ <3 empty items> ]（疎配列なので map が要素を飛ばす）
new Array(3).fill(0).map((_, i) => i + 1); // [1, 2, 3]（fill で埋めれば動くが 2 段階になる）
```

`new Array(n)` だけでは中身が空の疎配列になり、map は空のスロットを飛ばすので連番になりません（ch07/ex02 で `fill(0)` を挟んだのはこのため）。Array.from は疎配列を作らず、足りない要素を undefined として第 2 引数の関数に渡すので、1 回で作れます。なお、スプレッド構文も Array.from と同じ ES6 で入ったので、「既にある記法に後から足した」わけではありません。

**出典**:

- [MDN: Array.from()](https://developer.mozilla.org/ja/docs/Web/JavaScript/Reference/Global_Objects/Array/from)

## Q8. p.175 疎な配列の方がメモリ効率がよくなる。というのが良く分からなかったです。密な配列と同等の要素数を持つ疎な配列と密な配列を比較した時、疎な配列の方がメモリ確保するサイズが小さいのでしょうか。そうであるならば、なぜそうなるのでしょうか

**質問の要約**: 同じ length なら疎な配列のほうが確保するメモリが少ないから効率がよいのか、そうならどういう仕組みでそうなるのかを聞いている

**回答**: はい、確保するメモリが少なくなるからです。密な配列は、添字ごとに 1 つずつ場所を並べた連続した領域で持つので、穴の分も場所が要ります。一方、穴が多い配列は、エンジンが実在する要素だけを「添字と値の組」で持つ辞書形式に切り替えるので、穴の分の場所が要りません。

**補足**: たとえば `a[1000000] = 1` だけの配列は、length は 1000001 ですが要素は 1 つです。連続した領域で持つと 100 万個分の場所が要りますが、辞書形式なら 1 つ分で済みます。ただし辞書は 1 要素ごとに添字・値・属性をまとめて持つので、1 要素あたりはむしろ大きく、取り出しも少し遅くなります。得をするのは穴が多いときだけです。

疎な配列のアクセスが遅い理由は 2 つあります。

- 場所を計算で求められない: 密な配列は「添字 × 1 要素の大きさ」で格納位置が決まるので、探さずに直接取り出せます。辞書形式では、添字からハッシュ値を計算し、表の中から一致する添字を探す手間がかかります。
- 穴のときに探す範囲が広がる: 穴の位置を読むと、その配列には値がないので、プロトタイプチェーン（Array.prototype など）までたどって同じ添字のプロパティがないか確かめてから undefined を返します。V8 の公式ブログでも、穴のある配列は「追加のチェックと、プロトタイプチェーンをたどる高価な探索」が必要になると説明されています。

```js
// node --allow-natives-syntax で実行（%HasDictionaryElements は V8 のデバッグ用機能）
const sparse = [];
sparse[1000000] = 1;
%HasDictionaryElements([1, 2, 3]); // false（密な配列は連続した領域）
%HasDictionaryElements(sparse); // true（疎な配列は辞書形式）
```

**出典**:

- [MDN: Array（疎配列）](https://developer.mozilla.org/ja/docs/Web/JavaScript/Reference/Global_Objects/Array)
- [V8 公式ブログ: Fast properties in V8](https://v8.dev/blog/fast-properties)
- [V8 公式ブログ: Elements kinds in V8](https://v8.dev/blog/elements-kinds)

## Q9. p.175 メモリ効率を考えたりしながら設計を行う場合、どのようなことを意識していますでしょうか？（PCのスペックがどんどん高くなってきて、メモリ効率をあまり考えず実装したりAIに生成させたりしているが、メモリ効率を考えながら設計できる方がいいと思い質問させていただきました）

**質問の要約**: メモリ効率を意識して設計するとき、具体的に何に気をつけるかを聞いている

**回答**: JavaScript には、C 言語などと違って、いらなくなったメモリを自動で解放する仕組みがあります。ただ、どこかから参照が残っているものは解放されないので、いらなくなったものへの参照を残さないことを意識します。

**補足**: この自動で解放する仕組みをガベージコレクションと呼びます。参照が残りやすいのは、プログラムが終わるまで生き続ける Map やグローバル変数、イベントリスナーです。たとえば、ずっと生きている Map に入れたまま消さないと、使わなくなったオブジェクトも解放されず、メモリが増え続けます（メモリリーク）。オブジェクトに情報をひもづけたいだけなら、Map の代わりに WeakMap を使うと、そのオブジェクトがほかから参照されなくなったときに一緒に解放されます。

参照が残る具体例は次のとおりです。

```js
// 例 1: 参照が消えれば解放される
let user = { name: "A" };
user = null; // { name: "A" } はどこからもたどれなくなり、解放される
```

```js
// 例 2: ほかに参照が残っていると解放されない
let user = { name: "A" };
const list = [user]; // 配列からも参照している
user = null; // list[0] がまだ参照しているので、{ name: "A" } は解放されない
```

**出典**:

- [MDN: メモリー管理](https://developer.mozilla.org/ja/docs/Web/JavaScript/Guide/Memory_management)

## Q10. p.186 push()やpop()メソッドを使用すると、元の配列も変化してしまいますが、実装する関数によっては元の配列を変化させないように実装したりしたりすることは多いのでしょうか？

**質問の要約**: 元の配列を書き換えない（非破壊的な）実装をすることは実務で多いのかを聞いている

**回答**: 多いです。引数で受け取った配列を書き換えると、呼び出し元にも影響して不具合の原因になるので、新しい配列を返す書き方がよく使われます。たとえば React の state では、配列を push で書き換えても同じ配列のままなので変更として検知されず、画面が更新されません。そのため ES2023 で、sort や reverse の非破壊版である toSorted、toReversed、toSpliced、with も追加されました。

**補足**: 追加なら `[...arr, x]`、削除なら `arr.slice(0, -1)` や `filter` のように、新しい配列を作る書き方で push や pop の代わりにできます。React の state のように「別の配列になったこと」で変更を検知する仕組みでは、非破壊が前提になります。

React は state が変わったかを、古い値と新しい値が同じ配列そのものかどうか（`Object.is` による参照の比較）で判断します。

```js
const [items, setItems] = useState([1, 2]);

// 🚩 うまくいかない
items.push(3); // 元の配列を書き換える
setItems(items); // 渡しているのは同じ配列

// ✅ うまくいく
setItems([...items, 3]); // 新しい配列を作って渡す
```

push で中身は `[1, 2, 3]` に変わっていますが、setItems に渡しているのは元と同じ配列です。`Object.is(古い items, 新しい items)` が true になるので、React は「変わっていない」と判断して画面を描き直しません。スプレッド構文で別の配列を作れば false になり、変更として検知されます。

**出典**:

- [MDN: Array.prototype.toSorted()](https://developer.mozilla.org/ja/docs/Web/JavaScript/Reference/Global_Objects/Array/toSorted)
- [React: useState](https://react.dev/reference/react/useState)
- [React: state 内の配列の更新](https://react.dev/learn/updating-arrays-in-state)

## Q11. p.192 ソート自体は基本的に「比較→交換」の流れで行われると思いますが、一般的な計算量では比較がその多くを占めることが多い気がします。交換の計算量が十分に大きく、アルゴリズム全体の計算量に対して支配的になるケースってありますか？

**質問の要約**: ソートで、比較より要素の入れ替え（移動）のコストが支配的になる状況はあるかを聞いている

**回答**: あります。大きなデータを値ごとコピーする場合は、移動のコストが支配的になります。そのときは交換回数の少ない選択ソートを使ったりします。

**補足**: 交換のコストを減らすもう 1 つの方法は、データそのものではなく、データを指す参照（ポインタや添字）を並べ替えることです。参照は小さいので、データがどれだけ大きくても交換は安く済みます。たとえば C 言語の構造体の配列は中身がそのまま並ぶので、交換のたびに構造体全体をコピーしますが、ポインタの配列を作って並べ替えればコピーは避けられます。JavaScript の配列は、もともとオブジェクトの中身ではなく参照を持っています。そのため、何もしなくてもこの形になっていて、交換は安く済みます。

**出典**:

- [MDN: Array.prototype.sort()](https://developer.mozilla.org/ja/docs/Web/JavaScript/Reference/Global_Objects/Array/sort)
- [MDN: オブジェクト参照](https://developer.mozilla.org/ja/docs/Glossary/Object_reference)

## Q12. p.192 標準の sort は、内部でどんなアルゴリズムが使われているのでしょうか。実務で、計算量を意識して、アルゴリズムを選ぶ場面はありますか

**質問の要約**: Array.prototype.sort の中身のアルゴリズムと、実務で計算量を考えてアルゴリズムを選ぶことがあるかを聞いている

**回答**: 仕様ではアルゴリズムは決まっていませんが、V8 では TimSort が使われています。TimSort は、挿入ソートとマージソートを組み合わせたアルゴリズムです。実務でアルゴリズムを自分で選ぶことはまずありませんが、使うメソッドやデータ構造を選ぶときに、その計算量を意識して用途に応じて使い分けることは大事です。

**補足**: 仕様が求めているのは、ES2019 から「安定ソート（同じ値どうしの順番が元のまま保たれる）であること」だけです。V8 は以前、短い配列には挿入ソート、それ以外にはクイックソートを使っていましたが、安定でなかったため、V8 v7.0（Chrome 70）で TimSort に切り替えました。

同じことをするメソッドでも、計算量が違う例は次のとおりです。

| やりたいこと        | 配列のメソッド                       | Set / Map のメソッド                                    |
| ------------------- | ------------------------------------ | ------------------------------------------------------- |
| 値があるか調べる    | `includes`：先頭から順に探す（O(n)） | `Set` の `has`：線形探索より速い（ハッシュ表なら O(1)） |
| ID で要素を取り出す | `find`：先頭から順に探す（O(n)）     | `Map` の `get`：線形探索より速い（ハッシュ表なら O(1)） |

O(n) は「件数に比例して時間がかかる」、O(1) は「件数が増えてもほぼ一定の時間で済む」という意味です。Set と Map は、仕様で「平均して線形探索より速いこと」が求められています。

```js
const users = [
  { id: 1, name: "A" },
  { id: 2, name: "B" },
  // ...1 万件
];

// 配列の find: 毎回先頭から探すので、件数が増えるほど遅くなる
users.find((u) => u.id === 9999);

// Map の get: 最初に Map を作っておけば、件数が増えてもすぐに取り出せる
const userMap = new Map(users.map((u) => [u.id, u]));
userMap.get(9999);
```

1 回だけ探すなら配列の find で十分です。ループの中で何度も探す場面では、件数が多いほど差が大きくなるので、Set や Map に変えてから探します。

## Q13. （ページ不明）文字列の長さを求める適切な方法はありますでしょうか？ "aaa".length で求まりますが、文字列にサロゲートペアが入ると、見た目上の文字数よりも多くなってしまいます。Intl.Segmenter('ja', { granularity: 'grapheme' }) を使う方法もありますが、言語を指定しないといけないので、上手くやる方法ないのかなと思いました

**質問の要約**: サロゲートペアを含む文字列で、見た目どおりの文字数を数える方法と、Intl.Segmenter で言語指定を省けるかを聞いている

**回答**: サロゲートペアだけが問題なら、for/of や [...str].length で数えられます。文字列はコードポイント単位で反復されるので、サロゲートペアは 1 文字として扱われます。結合された絵文字まで 1 文字として数えたいなら Intl.Segmenter を使います。引数はどちらも省略でき、ロケールはランタイムのデフォルト、granularity は grapheme になるので、new Intl.Segmenter() だけで書けます。

**補足**: for/of でも、ゼロ幅接合子（ZWJ）でつないだ絵文字は分かれてしまいます。たとえば家族の絵文字 "👨‍👨‍👧‍👧" は、length が 11、for/of では 👨, ZWJ, 👨, ZWJ, 👧, ZWJ, 👧 の 7 回ループし、見た目どおりの 1 文字として数えられるのは Intl.Segmenter だけです（ch07/ex09 で確かめた内容）。
